## PHASE 2: new window shell (STOP after)
Replace the single 600×54 main window with a shell manager. Windows are created from Rust (pattern from capture.rs); the frontend routes by getCurrentWindow().label (pattern from main.tsx).
Hard requirements for EVERY shell window (strips, buttons, answer): always on top of everything, including other topmost windows and borderless fullscreen; invisible to screen capture (contentProtected, verify); not in the taskbar or Alt+Tab; never blocks clicks outside its own visible UI; does not steal focus from the app beneath when clicked (except while I type in the answer window's chat).
2.1 Hit-testing: windows must be TIGHT (window rect = visible UI, no large transparent areas). set_ignore_cursor_events applies to the whole window, not to a region, so use it only where needed (e.g., a glow margin), with dynamic toggling via cursor polling in Rust. Explain the approach you chose.
2.2 Always-on-top (Windows): natively via the windows crate: WS_EX_TOPMOST|WS_EX_TOOLWINDOW|WS_EX_NOACTIVATE and a watchdog thread that re-asserts SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE|SWP_NOMOVE|SWP_NOSIZE) about every second for all shell windows. macOS: the existing tauri_nspanel + high window level + collectionBehavior. Linux: best effort. Document the exclusive-fullscreen limit.
2.3 Three UI states (setting ui_mode, switchable from settings and by hotkey, persisted):
 - A "side strips": two tall narrow windows (default 56 px wide, ~60% of monitor height) at the left and right screen edges. Each can be dragged ONLY horizontally (x changes, y fixed), clamped to the monitor.
 - B "top/bottom strips": two wide short windows (default ~60% of monitor width, 56 px tall) at the top and bottom. Each can be dragged ONLY vertically.
 - C "buttons": no strips; every action is its own tiny window (~44×44) that is freely and independently draggable. Optional "shimmer" (animated rainbow/gradient glow, toggle and speed in settings, default ON) so the buttons are hard to lose.
 - Strip/button contents (same action set in all states, sensibly split across the two strips): Listen on/off, screenshot (manual), continuous mode on/off, open/close answer window, chat, TTS on/off, state/mode switcher, settings/dashboard. Show state badges (listening, later rate-limit/neutral).
 - Safety: a global "reset layout / find buttons" hotkey that restores default positions, raises everything to the top, and flashes the shimmer. Persist positions per monitor in a Rust-side JSON file (app data dir), not localStorage (several windows).
 - Axis-locked dragging: implement it yourself (pointer events + a Rust command that sets the position with the locked axis), because data-tauri-drag-region cannot lock an axis. Handle DPI scaling and multiple monitors.
 - Existing hotkeys: "hide/show" now hides/shows all shell windows; remove or adapt the old arrow-key window movement.
2.4 Answer window (label answer): centered on first open, movable (free drag by the header), resizable, an opacity setting (semi-transparent allowed), same hard requirements. Layout: header (title, placeholders for rate-limit/neutral status, close), two panes: MAIN (primary answer) and SIDE (secondary: side questions, quick analysis of what was scanned), plus a chat input at the bottom (typed questions join the single-request pipeline from Phase 3). Reuse the existing Markdown/KaTeX rendering and message-history components.
2.5 Add every new window label (strip-*, button-*, answer) to the capability files.
Acceptance: I can test each state; clicks pass through to apps beneath everywhere outside the UI; "covered-by" tests: a maximized app, a topmost window (Task Manager with "always on top"), a borderless fullscreen video: the overlay stays on top; OBS (window/display capture), Win+Shift+S and PrintScreen do not show it (report the results; the report contradicts itself about PrintScreen/Win+Shift+S: verify by reading the wry/tao sources and via GetWindowDisplayAffinity, and tell me which exact flag is applied).

## PHASE 3: capture, continuous mode, vision
3.1 A supportsImages (yes/no) setting per brain provider/model: an explicit toggle in settings that overrides auto-detection.
3.2 Capture settings (Screen Capture page): manual / interval / after speech ends; interval (>= 2 s); monitor (primary/all/specific); max frames per request (default 3); downscale of the longer side (default 1024 px) and JPEG quality (default 70; use JPEG instead of PNG for requests); frame-dedup threshold (perceptual hash/diff).
3.3 Continuous mode ("mode 3") per §5.1: a Rust interval loop (xcap) + dedup + downscale + event; audio from system AND microphone as two labeled channels ("[system]", "[mic]"). The report says there is a single stream: implement mic capture in Rust (cpal) or reuse the frontend VAD, whichever is simpler and more reliable; keep VAD speech segmentation. Batcher: collects transcript segments + changed frames + any typed question and sends ONE request when (a) speech has ended, or (b) the screen changed and a max wait of N s elapsed, or (c) I typed a question. Rules: one request in flight at a time, newer context replaces stale queued context, nothing is sent if nothing changed. Questions from the answer window join the same stream.
3.4 Vision for text-only models: when supportsImages=false, build a text "SCREEN CONTEXT" from frames according to a vision_mode setting: ocr (Windows.Media.Ocr via the windows crate first; cross-platform fallback RapidOCR/ort or tesseract), ocr+ui (adds the UI Automation tree of the foreground window: names/roles/values, capped by depth and characters), vlm (a separately configured vision-capable model, local Ollama or cloud, returns a description), full (everything combined, only on changed frames, in parallel). Output compact structured text with a size cap; the brain gets it as extra context. Check library currency online if possible and state what you chose and why.
Acceptance: unit tests for dedup and the batcher; manually: a text-only model answers questions about what is on screen; the request count stays bounded.
